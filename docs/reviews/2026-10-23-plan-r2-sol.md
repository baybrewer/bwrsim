New comments

1. [major] C1/C2/C3/C4, checkpoint event delivery - The host publish cursor measures snapshot construction, not UI consumption. The worker can construct a snapshot containing events 1-5 and advance its cursor, then release the lock before emitting it. A concurrent save_prepare returns only events after 5; its invoke response can be ingested and saved before the worker event arrives. The resulting save permanently omits events 1-5. Conversely, checkpoint events are replayed by the next worker publish because prepare does not advance the cursor. RunId filtering handles neither same-run case - Supply the UI's last consumed annunciator sequence to checkpoint preparation and return all subsequent events through the checkpoint watermark. Persist/restore that watermark with the record, deduplicate by runId/annunciator sequence, and add snapshot revision ordering so a delayed pre-checkpoint snapshot cannot replace newer state. Test delayed worker emission around prepare/write and overlapping checkpoint/worker event batches.

2. [major] C3, reset cursor after load - Reset consumption sets publish_cursor to the sim's latest sequence at worker execution time. After load_commit releases the lock, an operator command can run before the worker consumes reset; for example ManualScram adds an onset to the restored run. Reset then moves the cursor past that new event, silently discarding it without annEventsTruncated - Capture the restored event watermark at commit and install that exact cursor under the same lock, or carry the captured watermark in the reset request. Worker reset must never skip post-commit events. Test load_commit -> ManualScram -> worker reset before the first publish.

3. [major] C1/C3, scenario transition cursor - LoadScenario replaces the engine with a new Sim, including a new event sequence, but C3 only specifies resetting the publisher cursor on restore. A host cursor at 500 queried against a new run starting at seq 1 suppresses its first 500 events; runId filtering cannot recover events absent from snapshots. The new scenario also inherits host backlog unless this transition raises the clock reset - Apply the host transition/reset protocol to every successful LoadScenario, atomically initialize its event cursor for the new run, and reset host timing before advancing it. Test a scenario switch after a high event sequence, including switching while paused and immediately resuming.

4. [major] C1/C4, rejected-step annunciators - C1 captures transitions only during accepted steps and after apply. Sim::reject_step in crates/bwr-core/src/sim.rs rolls physics back, sets model_error, pauses, and inserts the model_limit operator event before returning false. With no later accepted step or command, those visible alarms never enter the sequenced event stream. A UI model-error baseline can supply the separate system entry but cannot supply the missing annunciator onsets - Finalize annunciator diffing after every externally visible step outcome, including rejection, while excluding rolled-back intermediate physics alarms. Exercise a vessel or condenser rejection followed by no further commands and assert both condition and operator-event onsets reach the log exactly once.

5. [major] C1, scenario initialization and event timestamps - Sim::full_power runs settle(600) and settle(120), both through step(), then resets time to zero and clears transient events. Adding transition recording to every accepted step also records initialization alarms with times up to 720 s. The proposed constructor contract does not clear/rebase that ring or its comparison baseline, so publishing the new run can inject warm-up alarms with timestamps later than its current time - Establish an explicit end-of-initialization boundary: suppress warm-up event recording or clear its ring, reset the sequence/baseline, then record initial visible alarms at run time zero. Test FullPower construction and LoadScenario into FullPower, asserting no warm-up transitions or future-dated entries are published.
